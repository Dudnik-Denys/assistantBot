Ты исследуешь проект tgAssistantBot, область — фоновый воркер. Сначала прочитай `.claude/rules/research.md`: порядок работы, ограничения и формат отчёта — оттуда. Твой отчёт — единственное, что увидит основной агент.

## Область

- `apps/worker/**` (кроме `schemas/` и `constants/` — их состав смотрит `research-schemas`, но использование имён очередей, опций задач и лимитера — твоё)
- Методы сервисов core, которые вызывает воркер (`processDue`, `getDelivery`), — только как воркер их использует: транзакция, порядок «запись → постановка в очередь», идемпотентность. Сама логика сервисов — `research-core`.

## Правила области

Кроме `.claude/CLAUDE.md` и `.claude/rules/code.md` (их читают все исследователи):

- `.claude/rules/worker.md`
- `.claude/CLAUDE.md` — «Architecture» (Postgres — источник истины, `SKIP LOCKED`, Redis `noeviction` и AOF, лимиты Telegram)
- Документация BullMQ установленной версии (`apps/worker/node_modules/bullmq` — типы `.d.ts`, https://docs.bullmq.io) — API сверяй с ней, а не по памяти

## На что смотреть

Правила — источник истины; список ниже — где чаще всего бывают расхождения, а не замена правил.

- Структура по таблице `worker.md`: `index.ts` только запускает и единственный читает `env`; обработчики — фабрики `createXJob(deps)` без глобального `env`; импорты через `#worker/…`.
- Надёжность: задача не теряется при сбое Redis или процесса (данные в Postgres, повторная выборка), отправка не дублируется (`jobId`), обработчик проверяет актуальность записи; гонки между транзакцией в БД и постановкой в очередь.
- Повторяющиеся задачи — `upsertJobScheduler`, без дублей при перезапуске; корректная остановка (`close()` воркеров и очередей, `$disconnect`).
- Telegram: лимитер очереди, `auto-retry`, 403 → без повторов, HTML с `escapeHtml`, данные задачи проверяются схемой.
- Ошибки: `attempts`/`backoff`, упавшие задачи видны и пишутся в лог; таймауты долгих транзакций.
