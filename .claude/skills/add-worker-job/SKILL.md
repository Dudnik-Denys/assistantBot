# add-worker-job

Добавь фоновую задачу: `$ARGUMENTS`

Источник принципов — `.claude/CLAUDE.md` («Architecture»: воркер — отдельный процесс; напоминания — данные в Postgres с `nextRunAt`, а не cron на каждое; периодическая задача раз в минуту выбирает наступившее через `SKIP LOCKED`; Redis — `noeviction` и AOF; лимиты Telegram — лимитер очереди и `@grammyjs/auto-retry`). Общие правила — `code.md`, `core.md`, `db.md`, `tests.md`. Перед началом проверь по официальной документации BullMQ актуальный API (`Queue`, `Worker`, `upsertJobScheduler` для повторяющихся задач, `limiter`) — не по памяти.

## 1. Каркас воркера (если `apps/worker` ещё нет)

Покажи план и дождись подтверждения — это новое приложение:

- `apps/worker` по образцу `apps/bot`: `package.json` (`dev` с `--env-file=../../.env`, `start`, `check`), `tsconfig.json`, алиас `#worker/*`, `src/index.ts` (только запуск, единственный читает env), `src/env.ts` через `parseEnv` и `src/schemas/env.ts` (`DATABASE_URL`, `REDIS_URL`, `BOT_TOKEN` для отправки).
- `src/queues/` — объявления очередей (имена — константы в `src/constants/`), `src/jobs/<задача>.ts` — обработчики (тонкие: вызов сервиса core), `src/schedulers.ts` — повторяющиеся задачи.
- Корректная остановка (`worker.close()`, `queue.close()`, `db.$disconnect()` по SIGINT/SIGTERM) — как у бота.
- Правило `.claude/rules/worker.md` (структура, как добавить задачу) — по аналогии с `bot.md`; строки в `CLAUDE.md` («Project status», «Commands») и README (`REDIS_URL` уже описан); `dev` подхватит `apps/*` сам.
- Отдельный агент `research-worker` и область `worker` в `/research` — после того как воркер появится.

## 2. Задача

1. **Данные — в Postgres.** Что и когда выполнить, хранится в модели (`nextRunAt`, статус, `userId`); логика выбора и сдвига (`nextRunAt` по правилу повтора в часовом поясе пользователя, хранение в UTC) — в сервисе core, с тестами. Redis — только транспорт: потеря очереди не теряет задачу.
2. **Периодическая выборка**: повторяющаяся задача (раз в минуту) берёт пачку наступивших записей `SELECT … FOR UPDATE SKIP LOCKED` (`$queryRaw` по `db.md`), ставит отправку в очередь и сдвигает `nextRunAt` в той же транзакции.
3. **Идемпотентность**: `jobId` из id записи и времени запуска — повтор не дублирует отправку; обработчик проверяет, что запись ещё актуальна.
4. **Отправка в Telegram**: лимитер очереди под лимиты (~30 сообщений/с всего, ~1/с в один чат), `auto-retry` на API бота; ошибки «бот заблокирован пользователем» — не повторять бесконечно, а пометить в данных.
5. **Повторы и ошибки**: `attempts` и `backoff` у задач; неожиданная ошибка — в лог с id задачи; задачи, исчерпавшие попытки, видны (не удаляются молча).

## 3. Тесты и проверка

Integration: сервис выборки и сдвига на тестовой БД (наступившие/будущие, чужие пользователи, часовые пояса и переход на летнее время — unit для вычисления). Обработчик — с подменённой отправкой в Telegram (функция-зависимость), без настоящего Redis, если логика от него не зависит. `bun run format`, `verifier` (`server`). Ручная проверка — `/dev-start` и созданная запись с ближайшим временем.
