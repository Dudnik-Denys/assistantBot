# architecture-design

Спроектируй: `$ARGUMENTS`

Роли (CLAUDE.md, «Распределение работы»): решения принимает основной агент (Opus) в этом скилле, код пишет `implementer` (Sonnet) по спеку, проверяет `verifier`. `effort: xhigh` действует на ход, в котором скилл запущен, — на нём делается разбор и черновик; дальнейшие ходы диалога идут на уровне сессии. Если пользователь хочет весь диалог на xhigh — `/effort xhigh` вручную.

## 1. Понять задачу

- Прочитай `.claude/CLAUDE.md` (функции MVP, архитектура, принципы) и правила областей, которые задача затронет (`code.md`, `core.md`, `db.md`, `api.md`, `svelte.md`, `components.md`, `ui.md`, `tests.md`, `bot.md`, `worker.md`).
- Новый модуль Mini App — ещё `.claude/skills/add-new-module/SKILL.md`: вопросы раздела 1, готовые части раздела 3, шаги раздела 4 и `templates/`.
- Изучи существующий код, на который задача опирается: похожий модуль (заметки, счётчики), связанные сущности, общие компоненты и `lib/reactive/`. Решение должно встраиваться в то, что есть, а не дублировать его (`code.md`, DRY).
- Чего не хватает — спроси одним сообщением, списком, с вариантами и рекомендацией.

## 2. Решение

Покажи пользователю — до кода:

- модель данных: поля, типы, ограничения, значения по умолчанию, индексы, связи;
- сервис core: методы, ввод и ошибки; эндпоинты API; клиент;
- экраны и из каких готовых частей; новые общие компоненты (только при втором реальном случае);
- бот и воркер — если нужны (`bot.md`, `worker.md`; напоминания — модель с `nextRunAt`, CLAUDE.md, «Принципы»);
- тесты: unit, integration, e2e (что проверить);
- что сознательно не делается сейчас;
- спорные места — варианты с рекомендацией.

**Жди подтверждения.** Правки пользователя — в решение, и снова показать изменённое.

## 3. Спек

Заполни `.claude/templates/spec.md` → `docs/designs/<имя>.md` (имя — латиницей, как модуль: `reminders.md`). Всё решённое — явно: исполнитель историю диалога не видит. В разделе «Правила, которые прочитать» — только нужные. Таблица файлов — полная. Если работа большая — разбей на этапы (core + API + тесты; затем экраны; затем бот), каждый — отдельный запуск исполнителя по своему разделу спека.

## 4. Исполнение и проверка

1. Миграция — до исполнителя, если она нужна раньше кода: модель в `schema.prisma` и `/migration` (подтверждение пользователя). Иначе — после, по отчёту исполнителя.
2. `implementer` с заданием: путь к спеку (и этап). Модель и усилия — из его файла (Sonnet, high).
3. Отчёт исполнителя: «Остановлено: нужен ответ» — ответь сам, если решение следует из уже согласованного, иначе спроси пользователя; дополни спек и продолжи того же исполнителя (`SendMessage`).
4. Ревью диффа (`git diff`): соответствие спеку и правилам. Мелкое — поправь сам; существенное — исполнителю с конкретными замечаниями.
5. `verifier` — по CLAUDE.md, «Commands»: тесты (`unit`, `integration`, `e2e` — Haiku, по очереди), затем `ui` / `server` / `all` (Sonnet). Падения — по `/fix-bug` (сначала `bug-fixer`).
6. Документация — по шагу 9 `add-new-module` (CLAUDE.md, `components.md`).

## 5. Отчёт

Что сделано по этапам, файлы, результаты проверок, отклонения от спека, список ручных проверок в Telegram (как в `add-new-module`, раздел 5). Не коммить.
