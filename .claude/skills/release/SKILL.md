# release

Выпусти версию: `$ARGUMENTS`

Нужен настроенный продакшен (`/deploy-setup`): `docker-compose.prod.yml`, workflow сборки, сервер с `/opt/tgab`. Нет — скажи и предложи `/deploy-setup`. Каждое действие на сервере и создание тега — **после подтверждения** пользователя.

## 1. Готовность

- Ветка `main`, рабочее дерево чистое, всё запушено (`git status`, `git log origin/main..HEAD`).
- CI на последнем коммите зелёный: `gh run list --branch main --limit 1`.
- Что входит в выпуск: `git log --oneline <прошлый тег>..HEAD` — сгруппируй для заметок (новое, исправления, внутреннее).
- **Миграции** с прошлого выпуска (`git diff --name-only <прошлый тег>..HEAD -- packages/db/prisma/migrations`): есть ли разрушающие (`DROP`, смена типа, `NOT NULL`) — предупреди отдельно, они необратимы.
- Новые переменные окружения (схемы env, README) — их нужно добавить в `.env` на сервере до выпуска.

## 2. Версия и сборка

Версия — semver (без аргумента предложи следующую: patch — только исправления, minor — новое). Тег `v<версия>` → `git push origin v<версия>` → workflow собирает образы; дождись его (`gh run watch`). Образы есть в GHCR — дальше.

## 3. Выпуск на сервере

По SSH (`ssh deploy@<сервер>`), в `/opt/tgab`:

1. **Бэкап перед миграциями**: `sudo /opt/tgab/deploy/backup.sh` — если в выпуске есть миграции (обязательно) или по желанию.
2. Обновить `deploy/` и `docker-compose.prod.yml`, если менялись (копия из тега: `git archive` или `scp`), прописать `TAG=v<версия>`.
3. `docker compose -f docker-compose.prod.yml pull`, затем `up -d` — `migrate` отработает первым, приложения поднимутся после него.
4. Ошибка `migrate` — приложения не стартуют на новой версии: покажи лог (`docker compose logs migrate`) и остановись, не пытайся чинить базу руками.

## 4. Проверка

- `docker compose ps` — все сервисы `running`/`healthy`, `migrate` — `exited (0)`.
- `curl -fsS https://app.<домен>/healthz`; логи web и bot за первую минуту без ошибок (`docker compose logs --since 2m`).
- Ручная проверка пользователем: открыть Mini App в Telegram, основной сценарий изменённого модуля, `/start` у бота.

## 5. Откат

План — до выпуска, выполнение — по решению пользователя: прежний `TAG` и `up -d`. Миграции не откатываются: если новая схема несовместима со старым кодом — восстановление из бэкапа шага 3.1 (`/backup restore`), с потерей данных после него. Поэтому разрушающие миграции — отдельным выпуском после того, как код перестал использовать удаляемое.

## 6. Итог

Версия, что вошло (заметки для GitHub Release: `gh release create v<версия> --notes …` — после подтверждения), результат проверок, что проверить вручную.
