# cover-module

Покрой модуль e2e-тестами: `$ARGUMENTS`

Главный источник правил — `.claude/rules/e2e.md` (структура, Page Object, `step()`, проверки, flows, **гонки**, данные). Прочитай его целиком перед началом и следуй ему; общие правила тестов — `tests.md`, кода — `code.md`. Этот скилл задаёт порядок работы, а не дублирует правила.

## 1. Проверь аргумент

- **Аргумента нет** → ничего не делай. Попроси имя модуля и перечисли существующие: папки `apps/web/src/routes/` (кроме `api`).
- **Модуля нет** (нет `apps/web/src/routes/<модуль>/`) → перечисли существующие и попроси выбрать. Сам не выбирай.
- **`tests/e2e/<модуль>/` уже есть** → ничего не меняй сразу. Сообщи, что у модуля уже есть e2e-тесты (перечисли сценарии — файлы `*.spec.ts` и описания `test`), и спроси: дополнить их или выбрать другой модуль (перечисли модули без e2e-тестов). Только после ответа «дополнить» — режим дополнения: прочитай существующие экраны и сценарии, добавляй недостающее, не переписывай рабочее без причины.

## 2. Инфраструктура

Playwright подключён (`tests/playwright.config.ts`, `bun run test:e2e`, общие файлы `tests/e2e/`: `base.page.ts`, `step.ts`, `fixtures.ts`, `main-menu/`). Как устроено и как запускать — `e2e.md`, «Запуск и отчёт» и «Конфиг Playwright». Если чего-то из этого нет — сначала скажи пользователю, не восстанавливай молча.

## 3. Изучи модуль

Прочитай, чтобы тестировать реальное поведение, а не предполагаемое:

- страницы `apps/web/src/routes/<модуль>/` (список, редактор, создание, `+page.ts` с загрузкой и ошибками);
- компоненты `apps/web/src/lib/components/<модуль>/` и используемые `ui/`;
- API `apps/web/src/routes/api/<модуль>/` и сервис `packages/core/src/<модуль>/` — какие ошибки и ограничения видит пользователь (лимиты, пустой ввод, 404);
- существующие тесты `tests/unit/<модуль>/` и `tests/integration/<модуль>/` — что уже покрыто ниже (e2e это не дублируют).

## 4. Составь список сценариев и согласуй

Покажи пользователю список сценариев **до написания кода** и дождись подтверждения. Ориентир — несколько сквозных сценариев на модуль (`e2e.md`): основной путь (создать → увидеть → открыть → изменить → удалить), поиск, пустое состояние, ошибка (несуществующая запись по адресу, ошибка ввода), навигация «Назад». Для каждого — файл `*.spec.ts` и одна строка, что проверяется.

## 5. Идентификаторы элементов (`data-testid`)

По `e2e.md`, «Элементы и `data-testid`»: для каждого элемента, с которым будут работать сценарии, — константа в `TestId` (`apps/web/src/lib/constants/test-ids.ts`, создай файл, если его нет) и атрибут `data-testid={TestId.…}` в компоненте; компонентам `ui/` без `{...rest}` — добавь передачу атрибутов. Заодно проверь доступность по `ui.md` (у кнопки-иконки `aria-label`, у поля подпись) — тесты на неё не опираются, но правило действует. Элементы базовых компонентов `ui/` — в `TestId.Common` (ставит сам компонент); записи с одинаковым текстом или известным id — `testIdWithValue`; состояние (вкладка, переключатель) — через `aria-*`, а не класс; анимированным компонентам — `motion-reduce:transition-none`. Все правки кода приложения — отдельным списком в отчёте.

## 6. Напиши тесты

По `e2e.md`, в таком порядке:

1. Экраны модуля — `tests/e2e/<модуль>/<экран>.page.ts`, наследуют `BasePage`; разделы: элементы → действия → проверки `expect…` → удобные методы.
2. Компоненты, которых ещё нет в `tests/e2e/components/`, — только если элемент есть на нескольких экранах; существующие — переиспользуй.
3. Flows — `tests/e2e/<модуль>/flows/`: каждая последовательность действий, которая в одном тесте затрагивает два и более экрана (в том числе вход из `MainMenuPage`), — flow. Данные, которые сценарий не проверяет, — фабриками.
4. Регистрация экранов в `tests/e2e/fixtures.ts`.
5. Сценарии — `tests/e2e/<модуль>/<сценарий>.spec.ts`: шаги через `step()`, внутри — последовательные `await`; описания тестов и шагов — по-русски в именном стиле («Создание заметки», не «Создать заметку»).

Удаление и другие действия с подтверждением — через `answerDialog` из `BasePage` (`e2e.md`, «Диалоги»): без него Playwright молча отменит диалог. Удаление из списка — свайпом через `SwipeRowComponent` (`e2e.md`, «Удаление свайпом»), удаление с экрана элемента — отдельным сценарием.

Перед завершением пройди по списку «Гонки» из `e2e.md` для каждого нового файла: `await` у каждого действия и проверки, только web-first `expect`, никаких пауз, подписка на ответ до действия, тесты независимы.

## 7. Проверка

- `bun run test:e2e <модуль>` — всё проходит на всех трёх проектах-устройствах (маленький, средний, большой iPhone).
- Нестабильность: `bun run test:e2e <модуль> --repeat-each=3` — все повторы зелёные. Падение на повторе — это гонка: найди причину по «Гонкам», а не добавляй ожидание или `retries`.
- `bun run format`, `bun run lint`, `bun run check`.
- Тесты пишут только в тестовую БД (`postgres-test`); рабочую БД и `.env` не трогать.

## 8. Отчёт

- Таблица сценариев: файл — что проверяет — ✅ / ❌; как открыть Allure-отчёт (`bun run test:e2e:report`).
- Новые и изменённые файлы тестов.
- Правки кода приложения (`data-testid`, `TestId`, передача атрибутов в `ui/`, доступность) — отдельно, с причиной.
- Что осталось непокрытым e2e и почему (покрыто unit/integration или требует настоящего Telegram).
- Ничего не коммить: коммит делает пользователь.
