# fix-bug

Ошибка: `$ARGUMENTS`

Цель — найти **причину**, а не прятать симптом; исправить её по правилам проекта и закрепить тестом (`tests.md`: «Исправленная ошибка получает тест, который её воспроизводит»).

## 1. Материалы

Пути из аргумента — абсолютные или от рабочего стола (`~/Desktop/…`). Если материалов нет, а по описанию не понять, где и как воспроизводится, — спроси: шаги, ожидание и что вышло, устройство (iPhone / Android / Telegram Desktop / браузер).

- **Скриншоты** (`.png`, `.jpg`, `.heic`) — прочитай как изображения: экран, текст ошибки, состояние интерфейса, тема (светлая/тёмная), устройство.
- **Видео** (`.mp4`, `.mov`) — нарежь кадры во временную папку скрэтчпада: `ffmpeg -i <видео> -vf fps=4 <папка>/frame_%03d.png` (для коротких видео до ~5 с; для длинных — `fps=2` и только нужный отрезок `-ss`/`-t`). Смотри кадры по порядку: что сделал пользователь (жест, нажатие), что ожидалось, где поведение расходится. Нет `ffmpeg` — попроси пользователя поставить (`brew install ffmpeg`).
- **Логи** (`.log`, `.txt`, вставленный текст) — найди первую ошибку, а не последнюю: стек, время, апдейт бота (`← update N`), HTTP-код и путь (`/api/…`), сообщение Prisma или zod. Лог CI — упавший шаг и его вывод (`gh run view --log-failed`, если дан номер запуска).
- **Секреты** в материалах (токены, `initData`, строки подключения) — не повторяй их в ответе и не сохраняй; если они в логе — предупреди пользователя, что лог содержит секрет.

Итог шага — 2–4 строки: что видно, шаги воспроизведения, ожидание и факт.

## 2. Причина

1. По симптому найди код: экран → `routes/` и компоненты; запрос → эндпоинт `routes/api/` → сервис core; бот → роутер и middleware. `git log -p --since=…` по затронутым файлам — если ошибка появилась недавно.
2. Сформулируй гипотезу и **проверь её по коду** (поток данных, состояние, условия), а не подбором правок. Платформенные особенности (iOS Safari в Telegram, жесты, клавиатура, `viewport`) — сверь с документацией, а не по памяти; не уверен — скажи.
3. Если причин несколько или не хватает данных — назови варианты и что нужно, чтобы выбрать (лог, ещё одно видео, версию Telegram). Не исправляй вслепую.

Покажи пользователю причину (`путь:строка`, 2–4 предложения) и план исправления. Исправление, которое меняет поведение заметно для пользователя или затрагивает несколько модулей, — после подтверждения; очевидная локальная ошибка — сразу.

## 3. Тест, который воспроизводит ошибку

До исправления — тест, который **падает** на текущем коде (по `tests.md`): unit — для чистой логики, схем, `lib/http`, `lib/utils`; integration — для сервисов core и middleware бота. Логика с рунами и жесты (`lib/reactive`, компоненты) unit-тестами не покрываются — для них запиши сценарий в список для e2e (`e2e.md`) и ручную проверку (шаг 6). Прогони тест и убедись, что он падает по той самой причине.

## 4. Исправление

- Исправляй причину в правильном слое (логика — в core, транспорт — в эндпоинте или хендлере, отображение — в компоненте), по правилам `.claude/rules/` для затронутых файлов.
- Тот же дефект в похожих местах (`git grep` по шаблону) — исправь и их или перечисли.
- Не добавляй обходов «на всякий случай» (`try/catch` без обработки, задержек, флагов) без причины, которую можно объяснить.

## 5. Проверка

`bun run format`, затем `verifier` (режим по затронутому: `ui`, `server` или `all`). Тест из шага 3 теперь проходит.

## 6. Отчёт

1. Причина — 1–3 предложения, `путь:строка`.
2. Что изменено (файлы) и почему так.
3. Тест: файл и что проверяет; если тест невозможен — почему и что вместо него.
4. **Ручная проверка** — по шагам, на тех устройствах, где ошибка проявилась: что открыть (`/dev-start`, туннель), что сделать, что должно получиться. Отдельно — что проверить рядом, чтобы исправление ничего не сломало.
5. Строка коммита для пользователя (`/commit-plan`, если изменений много).
