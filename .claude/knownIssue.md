# Известные проблемы (knownIssue)

Проблемы, о которых знаем и которые сознательно оставили как есть. Если симптом из записи всплыл — начинать разбор отсюда, а не с нуля. Новая запись — по тому же образцу: что, когда появилось, почему так, как узнать, что это она, что можно сделать.

## 1. Повторное сообщение об окончании цикла счётчика

- **Когда появилась:** 2026-11-24, вместе с отправкой уведомлений через outbox (модуль «Счётчики», воркер `apps/worker`).
- **Симптом:** пользователь получает в Telegram одно и то же сообщение «⏰ Счётчик «…»: цикл завершён» дважды (с тем же номером цикла). В Mini App при этом одно уведомление.
- **Где:** `apps/worker/src/jobs/counter-notification.ts` — сначала `api.sendMessage(...)`, потом `notifications.markSent(id)` (поле `CounterNotification.sentAt`).
- **Почему происходит:** отправка в Telegram и отметка `sentAt` в Postgres — две разные системы, атомарно сделать обе нельзя. Если между ними что-то оборвалось — процесс воркера упал или перезапустился, БД недоступна в момент `markSent`, задача BullMQ упала после успешной отправки, — `sentAt` остаётся пустым. Через минуту outbox (`notifications.listUnsent` в `jobs/counters-due.ts`) снова находит уведомление и, если задачи с тем же `jobId` уже нет в Redis (упала после всех попыток и удалена outbox перед новой постановкой, Redis очищен) или она ещё повторяется после ошибки, отправляет его ещё раз.
- **Почему оставили:** это обычная семантика «хотя бы один раз» (at-least-once). Обратный порядок (сначала `sentAt`, потом отправка) даёт «не больше одного раза» — тогда при сбое сообщение терялось бы совсем. Для уведомлений редкий дубль лучше пропущенного. Окно — доли секунды между ответом Telegram и записью в БД.
- **Как убедиться, что это она:**
  - у уведомления в БД `sentAt` заполнен позже, чем пришло первое сообщение, или задача отправки в Redis (`counter-notification-<id уведомления>`) выполнялась больше одного раза (`attemptsMade` > 1);
  - в логах воркера около времени первого сообщения — падение или перезапуск процесса, ошибка подключения к Postgres, «Задача notifications/… не выполнена».
  - Если дубли частые и без сбоев рядом — это не эта проблема: искать, почему не срабатывает `markSent` или почему одно событие создаёт два уведомления (уникальный индекс `[counterId, finishedAt]` должен это запрещать).
- **Что можно сделать, если станет мешать:**
  - сохранять `message_id` ответа Telegram вместе с `sentAt` в одной записи и перед отправкой проверять, нет ли его уже (сократит окно, но не уберёт);
  - отправлять с ключом идемпотентности на стороне получателя — Telegram Bot API такого не поддерживает, поэтому полностью исключить дубль нельзя;
  - уменьшить число повторов задачи после успешной отправки: отметка `sentAt` — отдельным шагом с собственными повторами, а не частью задачи отправки.

## 2. Чёрный экран Mini App по кнопке из сообщения бота (только в разработке, ngrok)

- **Когда появилась:** 2026-11-24, вместе с кнопкой «Открыть уведомление» в сообщении об окончании цикла счётчика (воркер, `apps/worker/src/keyboards/open-notification.ts`). Записана 2026-11-26.
- **Симптом:** по «Открыть уведомление» Telegram показывает страницу бесплатного ngrok «You are about to visit …ngrok-free.dev … Visit Site»; после «Visit Site» Mini App остаётся чёрным. Кнопка «Открыть приложение» из `/start` при этом открывает приложение нормально (как правило — потому что промежуточную страницу уже прошли раньше).
- **Где:** не в коде проекта — в туннеле разработки (ngrok free). Адрес кнопки собирается верно (`MINI_APP_URL` + `NOTIFICATION_SCREEN_PATH` + id), маршрут `/reminders/notifications/[id]` есть.
- **Почему происходит (гипотеза, не подтверждена до конца):** бесплатный ngrok показывает промежуточную страницу браузеру без его cookie. Telegram передаёт данные входа в «хвосте» адреса (`#tgWebAppData=…`); после «Visit Site» страница открывается заново, видимо, уже без него — приложение стартует внутри Telegram без `initData` и темы, и WebView остаётся пустым. Пропустить страницу ngrok можно только заголовком `ngrok-skip-browser-warning` или своим User-Agent — WebView Telegram их не отправляет.
- **Почему оставили:** в продакшене свой домен без промежуточной страницы — проблемы нет; в разработке есть обходы (ниже).
- **Как убедиться, что это она:**
  - перед чёрным экраном была страница ngrok «You are about to visit»;
  - открыть приложение кнопкой из `/start` (пройти страницу ngrok, если покажется), закрыть и сразу нажать «Открыть уведомление» — если теперь открывается экран уведомления, это она;
  - если чёрный экран и без страницы ngrok (или в продакшене) — это не эта проблема: искать в коде (запуск `+layout.svelte`, `initTelegram`, загрузка `/reminders/notifications/[id]`).
- **Что можно сделать, если станет мешать:**
  - в разработке открыть приложение сначала через `/start` после каждого нового запуска туннеля;
  - перейти на Cloudflare Tunnel (`cloudflared tunnel --url http://localhost:5173` — без промежуточной страницы; адрес быстрого туннеля меняется при каждом запуске, постоянный — у именованного туннеля на своём домене) и обновить `MINI_APP_URL` и адрес Mini App у BotFather;
  - платный ngrok (без промежуточной страницы).

## 3. Mini App перезагружается после сворачивания Telegram (только в разработке, `vite dev`)

- **Когда появилась:** с начала разработки Mini App; записана 2026-11-26.
- **Симптом:** свернуть Telegram на iPhone (перейти в другое приложение или на рабочий стол) и вернуться — Mini App на мгновение показывает прежний экран, затем чёрный и загружается заново (с главного экрана, несохранённое состояние экрана теряется).
- **Где:** не в коде проекта — клиент HMR dev-сервера Vite (`vite/dist/client/client.mjs`, обработка `vite:ws:disconnect`: «[vite] server connection lost. Polling for restart...» → `location.reload()`).
- **Почему происходит:** при `bun run dev` страница держит WebSocket с dev-сервером Vite для горячей перезагрузки кода. В фоне iOS приостанавливает WebView, соединение рвётся; при возврате клиент Vite видит обрыв, ждёт сервер и перезагружает страницу. В продакшен-сборке (`bun run build:web`) клиента HMR нет — перезагрузки нет.
- **Почему оставили:** это поведение инструмента разработки, а не приложения; у пользователей его не будет.
- **Как убедиться, что это она:**
  - в консоли WebView (Safari → Разработка → iPhone) перед перезагрузкой — `[vite] server connection lost. Polling for restart...`;
  - на продакшен-сборке через тот же туннель (`bun run build:web && bun --cwd apps/web start`) перезагрузки нет;
  - если перезагружается и продакшен-сборка, и после короткого ухода в фон — это не эта проблема: смотреть, не выгружает ли iOS WebView из-за памяти, и восстановление состояния экрана.
- **Что можно сделать, если станет мешать:**
  - проверять поведение «как у пользователя» на продакшен-сборке (команда выше);
  - переключатель в `apps/web/vite.config.ts`: переменная окружения (например, `DEV_HMR=false`) выключает `server.hmr` — без перезагрузки при сворачивании, но и без горячей перезагрузки при правке кода (Mini App открывать заново вручную); переменную — в таблицу README.
