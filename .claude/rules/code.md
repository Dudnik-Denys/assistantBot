# Принципы кода

Действуют во всём проекте (TS, Svelte, Python, shell-скрипты вроде `run.sh`). Правила отдельных частей — в своих файлах: `core.md` (бизнес-логика), `api.md` (сервер и HTTP Mini App), `svelte.md` (Svelte и SvelteKit), `components.md` (компоненты), `ui.md` (вёрстка и стили), `bot.md`, `db.md`, `tests.md`, `e2e.md`.

## Переиспользование (DRY)

- Прежде чем писать новое, найди существующее: компонент в `src/lib/components/`, функцию в `src/lib/`, сервис или схему в `packages/core`. Расширь его, а не пиши параллельный вариант.
- Логика, повторённая второй раз, выносится: в функцию (`lib/errors.ts` → `errorMessage`), компонент (`ui/layout/Card`), константу или схему. Копировать блок с мелкими отличиями нельзя — отличия становятся параметрами.
- Константы предметной области (лимиты, форматы, значения по умолчанию) объявляются один раз, в `packages/core/src/constants/`, а не дублируются числами в разных слоях.
- Не обобщай заранее: абстракция появляется, когда есть второй реальный случай использования, а не «на будущее».

## Структура и ответственность

- Одна ответственность на модуль: сервис — бизнес-логика, эндпоинт и хендлер бота — только транспорт (разобрать запрос, вызвать сервис, вернуть ответ), компонент — отображение.
- Бизнес-логика — в `packages/core`; `apps/*` — тонкие слои над ней (см. CLAUDE.md).
- Зависимости передаются явно (БД, конфиг, другие сервисы — аргументами фабрики или конструктора), а не импортируются глобально внутри логики. Так код тестируется и заменяется.
- Инкапсуляция: модуль экспортирует только то, что нужно снаружи; внутренние детали (SQL, форматы хранения) не протекают в вызывающий код — наружу отдаются DTO.
- Ошибки предметной области — свои классы в core (`core.md`, «Ошибки»); транспортный слой (API, бот) переводит их в HTTP-коды или ответы в одном месте.
- Устройство `packages/core` (папки, сервисы-фабрики, публичный API) — `core.md`.

## Схемы zod

- zod-схема объявляется только в папке `schemas/` своего пакета — не в файле сервиса, роутера, env или теста. Внутри — папки модулей или групп (`schemas/notes/`, `schemas/common/`), файл — по теме схемы (`note-input.ts`, `list-query.ts`); в маленьком пакете без модулей — файл по теме прямо в `schemas/` (`apps/bot/src/schemas/env.ts`, `tests/schemas/env.ts`).
- В файле схемы — только схемы и выведенные из них типы (`z.infer` / `z.input`). Константы — в `constants/`, DTO — схемой ответа (`schemas/<модуль>/<сущность>-dto.ts`, тип выводится из неё), интерфейсы, которые из схем не выводятся, — в `types.ts` модуля, разбор и обработка ошибок (`safeParse`, `prettifyError`) — в коде, который схему использует. Env приложения разбирается одной общей функцией `parseEnv(схема, заголовок)` из `@tgab/core/env` (`env.ts` бота и воркера, `helpers/test-env.ts`): у приложения — только своя схема и заголовок сообщения.
- Схема, нужная нескольким пакетам, — в `packages/core/src/schemas/`; приложения и тесты импортируют её из core, а не пишут свою.
- Где лежат `schemas/`: core — `packages/core/src/schemas/`, бот — `apps/bot/src/schemas/`, воркер — `apps/worker/src/schemas/`, Mini App — `apps/web/src/lib/schemas/` (схемы только для web: `api-error.ts`), тесты — `tests/schemas/`. Исключение — `apps/web/src/env.ts`: SvelteKit ищет его по этому пути; схемы внутри него собираются из `@tgab/core/env`.

## ООП и паттерны

- Применяй базовые принципы ООП и SOLID там, где они упрощают код: единая ответственность, инкапсуляция состояния, композиция вместо наследования, зависимость от интерфейсов (типов), а не от конкретных реализаций.
- Сервисы core — фабрики, а не классы (`core.md`, «Сервисы»). Классы — там, где есть собственное изменяемое состояние или иерархия (ошибки, клиенты внешних API, реактивные классы Mini App).
- Паттерн выбирай под задачу и называй его в коде (имя модуля, комментарий), если он неочевиден: стратегия для источников погоды и вакансий, адаптер для внешних API, репозиторий не нужен поверх Prisma без причины.

## Форматирование и линтинг

- Biome — форматтер и линтер для всего, кроме `.svelte` (конфиг `biome.json`, правила `recommended`). Prettier с `prettier-plugin-svelte`, `prettier-plugin-tailwindcss` (порядок классов) и `@ianvs/prettier-plugin-sort-imports` (порядок импортов: пакеты → `#lib` → относительные, как у Biome) — только для `.svelte` (конфиг — ключ `"prettier"` в корневом `package.json`; отдельного `.prettierignore` нет, Prettier пропускает то, что в корневом `.gitignore`). Markdown не форматируется ни тем, ни другим.
- Стиль общий для обоих: табы, одинарные кавычки, запятые в конце многострочных списков, ширина строки 100.
- Содержимое шаблонных строк форматтеры не трогают — отступы в многострочных шаблонах (сырой SQL и т. п.) тоже только табами. Оформление сырого SQL — `db.md`, раздел «Доступ к данным и SQL».
- После изменений запускай `bun run format`; проверки перед коммитом (`bun run lint`, `bun run check`, `bun run test:unit`, `bun run test:integration`; правила тестов — `tests.md`) основной агент поручает субагенту `verifier` (CLAUDE.md, «Commands»). Предупреждения линтера исправляй, а не отключай; отключение правила — только с комментарием-причиной (`// biome-ignore lint/...: причина`).

## Именование и типы

- Имена — по смыслу и роли, а не по реализации: `elevation`, а не `black20`; `notesService`, а не `ns`.
- Без `any`; внешние данные (запрос, env, ответы API) проверяются схемой (zod) на границе, дальше по коду идут уже типизированные значения. Одна и та же проверка не пишется дважды: общие схемы — в `packages/core` (для env и аргументов CLI — `@tgab/core/env`: `optionalEnv`, `TelegramIdSchema`, `DatabaseUrlSchema`, разбор — `parseEnv`). Ручные `typeof`, регулярки и `JSON.parse` *вместо* схемы — нет. Разбор строки в значение перед схемой допустим (`JSON.parse` с `try/catch`, где ошибка разбора даёт `undefined`, а проверяет результат схема — как `parseJson` в `auth/init-data.ts`).
- Внешние данные не приводятся к типу через `as` (`as NoteInput` — нет): `as` выдаёт непроверенные данные за проверенные. Сервис core принимает ввод как `unknown` и разбирает схемой сам (`core.md`, «Сервисы»).
- zod-схемы называются `PascalCase` + `Schema` (`NoteInputSchema`, `TelegramIdSchema`); выведенный из схемы тип — тем же именем без суффикса (`NoteInput`). Короткие имена и сокращения (`n`, `s`, `k, v`, `e`, `res`, `cb`, `fn`) не используются нигде — ни в стрелочных функциях, ни в `catch`, ни в обработчиках событий: `note`, `text`, `[key, value]`, `catch (error)`, `(event: PointerEvent)`, `response`, `callback`. Если имя занято (`error` из `@sveltejs/kit`) — уточни по смыслу: `loadError`, `removeError`. Исключения — общепринятые имена библиотек (`z` из zod, `ctx` в grammY), параметры типов (`T`) и `fetchFn` — подменяемый `fetch` (как в `load` SvelteKit): там `Fn` — часть имени, которая отличает функцию от глобального `fetch`, а не всё имя.
- Числа со смыслом (лимиты, сроки, размеры страниц) — именованные константы, а не литералы в коде.
