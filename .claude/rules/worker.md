# Воркер (BullMQ, `apps/worker`)

Принципы — CLAUDE.md, «Architecture»: воркер — отдельный процесс; источник истины — Postgres, Redis — только транспорт задач (потеря очереди не теряет данные); Redis с `noeviction` и AOF. Общие правила кода — `code.md`, логика — `core.md`, SQL — `db.md`. API BullMQ сверяй с документацией установленной версии (https://docs.bullmq.io), а не по памяти. Новая задача — скилл `/add-worker-job`.

## Структура `apps/worker/src`

| Папка / файл | Что там |
|---|---|
| `index.ts` | Только запуск — единственное место, где читается `env` и создаются БД, сервисы core, `Api` grammY (только отправка, с `autoRetry`), очереди и `Worker`'ы; лог упавших задач; корректная остановка (`worker.close()`, `queue.close()`, `db.$disconnect()`) |
| `env.ts`, `schemas/env.ts` | `parseEnv(EnvSchema, заголовок)`; общие схемы (`DatabaseUrlSchema`, `RedisUrlSchema`, `MiniAppUrlSchema`, `optionalEnv`) — из `@tgab/core/env` |
| `constants/` | Имена очередей и задач (`QueueName`, `JobName`), id планировщиков, интервалы, лимитер, `attempts`/`backoff`/хранение задач, коды и пути Telegram |
| `queues/` | `createQueues(connection)` — объявления очередей |
| `schedulers.ts` | Повторяющиеся задачи: `upsertJobScheduler` (идемпотентен — перезапуск не создаёт второй планировщик) |
| `jobs/<задача>.ts` | Обработчики — фабрики `createXJob(deps)`: тонкие, вызывают сервис core; зависимости — аргументами |
| `schemas/` | Схемы данных задач: `job.data` из Redis не типизирован — разбирается схемой в обработчике |
| `messages/`, `keyboards/` | Тексты сообщений (HTML, пользовательские строки — `escapeHtml` из core) и inline-клавиатуры |

Импорты — через алиас `#worker/…` с явным расширением.

`ioredis` в `package.json` не импортируется, но нужен: это peer-зависимость BullMQ, клиент Redis BullMQ создаёт сам из `connection: { url }`. Не удалять как «неиспользуемую».

## Правила задач

- **Выборка наступившего** — в сервисе core (`counters.processDue`): пачка наступивших записей, каждая — в своей короткой транзакции с явным таймаутом (`COUNTER_TRANSACTION_TIMEOUT_MS`) и блокировкой строки `FOR UPDATE SKIP LOCKED`. Сбой одной записи не откатывает и не прерывает остальные: `processDue` ловит ошибку каждой записи и возвращает её в `failed` (воркер пишет в лог), а запись берёт следующий проход. Задача выборки обрабатывает не больше `COUNTERS_DUE_MAX_PASSES` пачек за запуск и останавливается, если в пачке ничего не завершилось, — иначе записи, которые раз за разом не завершаются, крутили бы её без конца. Та же транзакция одной записи может вызываться и вне воркера (`counters.finish` из Mini App, когда отсчёт дошёл до нуля): блокировка `SKIP LOCKED` и проверка статуса в ней делают двойную обработку невозможной. Тяжёлые вычисления — без перебора, где можно (досчёт пропущенных циклов делением).
- **Отправка — через outbox, а не из транзакции.** В транзакции событие только записывается в БД (`CounterNotification`, `sentAt = null`); Redis в транзакции не трогается — запись в две системы атомарной не бывает. Отдельный шаг периодической задачи берёт неотправленные (`notifications.listUnsent`, не старше `NOTIFICATION_RESEND_WINDOW_MS`) и ставит их в очередь; обработчик после отправки ставит `sentAt` (`markSent`). Сбой Redis, процесса или Telegram только откладывает отправку до следующего прохода.
- **Идемпотентность**: `jobId` задачи отправки — из id записи, которая уникальна для события (`counter-notification-<id уведомления>`; двоеточие в `jobId` BullMQ запрещено). Выполненные задачи хранятся сутки — повтор с тем же `jobId` игнорируется. Обработчик проверяет, что запись ещё есть и не отправлена (`getDelivery` → `null` — ничего не делать). Окно досылки (сутки) совпадает со сроком хранения выполненных задач, поэтому повторная постановка в пределах окна не создаёт дубль.
- **Telegram**: лимитер очереди отправки (`NOTIFICATIONS_LIMITER`, с запасом под ~30 сообщений/с), повторы при 429 и сбоях сети — `@grammyjs/auto-retry`. Ошибки, при которых этому пользователю не доставить никогда (`TELEGRAM_UNDELIVERABLE_CODES`: 403 — бот заблокирован; 400 — **любой**: чат не найден, пользователь деактивирован, но и некорректный запрос — решено не разбирать `description`: повтор 400 не исправит, а текст ошибки остаётся в логе задачи), — запись помечается недоставляемой (`deliveryFailedAt`, `markUndeliverable`), и outbox её больше не выбирает; задача завершается `UnrecoverableError`, без повторов (видна в логе); уведомление при этом остаётся в Mini App. 401 (неверный токен) — сбой настройки всего воркера: `UnrecoverableError` без пометки, после исправления токена outbox дошлёт. 429 и сбои сети — временные: их повторяет `auto-retry`, а затем `attempts`.
- **Повторы**: у отправки — `attempts` и экспоненциальный `backoff`; упавшая после всех попыток задача отправки хранится неделю (`removeOnFail: { age }` — видно, что и почему не ушло), а outbox перед новой постановкой удаляет её (`getJob` → `isFailed` → `remove`): иначе её `jobId` заблокировал бы повтор, и уведомление после долгого сбоя не дослалось бы, у периодической выборки хранятся 100 последних неудач (`removeOnFail: { count: 100 }`), выполненные выборки удаляются сразу. Всё упавшее пишется в лог с id задачи: у `Worker` — `on('failed')` и `on('error')`, у каждой `Queue` — `on('error')` (без слушателя BullMQ молча глотает сбой Redis при постановке задач). Данные задачи не той формы повтор не исправит — обработчик разбирает их `safeParse` и бросает `UnrecoverableError`, а не `ZodError` с пятью повторами.
- Отправка — «хотя бы один раз»: сбой между `sendMessage` и `markSent` даёт повторное сообщение. Это известная проблема — `.claude/knownIssue.md`, №1.
- Процессу бота воркер не мешает: обновления получает только бот (long polling), воркер лишь отправляет сообщения тем же токеном.
