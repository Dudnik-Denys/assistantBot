# Компоненты Mini App

Как устроены и где лежат компоненты, как объявляются props и как передаются различия. Стили и дизайн-токены — в `ui.md`, руны и SvelteKit — в `svelte.md`.

## Где лежат

Компоненты лежат в `src/lib/components/` по папкам:

- `ui/` — общие, не знают о предметной области, разложены по назначению:
  - `buttons/` — кнопки: `Button`, `BackButton`, `FloatingButton`, `SwipeDeleteButton` («Удалить» в действиях `SwipeActions`);
  - `layout/` — каркас экрана и контейнеры: `Screen`, `ScrollArea`, `PageHeader`, `ActionBar`, `Card` (карточка-ссылка), `Panel` (блок без перехода: группа полей, сведения), `SwipeActions` (строка списка с действиями по свайпу);
  - `feedback/` — состояния и отклик: `Message`, `Loading`, `Spinner`, `Notice`, `NavigationProgress`, `ProgressRing` (круговой прогресс), `ListState` (состояния экрана списка: ошибка, загрузка, «нет связи», пусто — и сам список через snippet);
  - `forms/` — поля ввода: `SearchBar`, `Field` (подпись сверху и текст поверх пустого поля — общая обёртка полей ниже), `TextField` (текст с подписью), `NumberField` (целое число), `DateField` (дата, системный календарь, значение — `Temporal.PlainDate`), `TimeField` (время, системный выбор часов и минут, значение — `Temporal.PlainTime`), `Switch` (флаг), `SegmentedControl` (выбор варианта: вкладки, режим);
  - `text/` — оформление текста: `SectionTitle`.

  Новый компонент кладётся в подходящую группу; если не подходит ни одна — заводится новая группа с понятным именем во множественном числе. Компоненты принимают данные и тексты через props, а не хардкодят их под конкретный раздел.
- `<раздел>/` — компоненты одной функции: `notes/` (`NoteCard`, `NoteEditor`), `counters/` (`CounterCard`, `CounterView`, `CounterForm`, `CounterStepper`), `reminders/` (`NotificationCard`, `NotificationView`) и т. д. Могут использовать `ui/`, но не компоненты другого раздела.
- Если компонент нужен двум разделам — он переезжает в `ui/` и обобщается.
- Импорт — всегда через алиас: `#lib/components/ui/<группа>/X.svelte`, `#lib/components/<раздел>/X.svelte`. Относительные пути между компонентами не используются, даже внутри `ui/`.

## Что внутри компонента

- В `<script lang="ts">` — только состояние компонента и связка с разметкой. Алгоритмы, запросы, форматирование, работа с Telegram — в модулях `src/lib/` (их можно тестировать и переиспользовать; куда именно — `svelte.md`, «Где лежит код в `src/lib`»). Повторяющаяся реактивная логика — класс в `lib/reactive/`.
- Внутри `.svelte` TypeScript только «типовой»: аннотации и типы. Конструкции, порождающие код (`enum`, parameter properties), — в `.ts`-файлах.
- Ключи в `{#each}` обязательны для списков, которые меняются: `{#each notes as note (note.id)}`.
- Константа одного компонента, которую больше никто не использует, остаётся в нём самом (`SHOW_DELAY_MS` в `Loading.svelte`); общие — в `lib/constants/` (`svelte.md`).

## Props

- Props объявляются в самом компоненте как `interface Props` (так в документации Svelte 5), деструктуризация — одной строкой: `let { title, onback }: Props = $props();`. Над интерфейсом — комментарий о компоненте, у неочевидных props — свой `/** … */` (виден в подсказке редактора там, где компонент используется). Типы props не выносятся в отдельные файлы: снаружи тип доступен как `ComponentProps<typeof X>`.
- Компонент, который пробрасывает HTML-атрибуты, расширяет их тип и передаёт остаток через `{...rest}`: `interface Props extends HTMLButtonAttributes { … }`.
- Общая часть props нескольких компонентов — в `src/lib/types/` и подключается через `extends`: `interface Props extends ClassProp { … }` (`types/props.ts` — `ClassProp`, внешний `class` для `mergeClasses()`). Сюда — только то, что действительно повторяется у нескольких компонентов, а не «на будущее». Компонент без своих props — `type Props = ClassProp`.
- Колбэки — свойства `on<действие>` (`onback`, `onremove`), а не события; свойство, которое компонент меняет для родителя, — `$bindable()`.

## Базовые компоненты и различия между экранами

- Компоненты в `ui/` — базовые и настраиваемые, а не под конкретный раздел: один `PageHeader` для всех экранов, а не `NotesHeader` и `CountersHeader`. Различия передаются снаружи:
  - данные — props (`title`, `onback`);
  - содержимое — snippets (`children` и именованные): поиск под заголовком, кнопки в `ActionBar`, действия в `SwipeActions`;
  - стили — prop `class`, который объединяется с базовыми классами через `mergeClasses()` из `#lib/utils/classes.ts`: `class={mergeClasses('базовые классы', className)}`.
- Класс снаружи объединяй только через `mergeClasses()`, не массивом и не склейкой строк: `mergeClasses` (tailwind-merge) убирает конфликтующие классы, и переданный снаружи `pb-6` надёжно заменяет базовый `pb-3`. Без него победит тот, что позже в CSS Tailwind, — почти случайно. Новые токены отступов из `app.css` регистрируй в `extendTailwindMerge` в `lib/utils/classes.ts`.
- Что выбрать для повторяющегося оформления:
  - повторяется разметка с поведением (шапка, панель, кнопка) → компонент в `ui/`;
  - повторяется только «вид» у элементов разного типа, и компонент не подходит (поле `<input>` и `<textarea>` без рамки; заполненное поле в `TextField`, `NumberField`, `DateField`, `TimeField`) → `@utility <роль>` в `app.css` (`field-bare`, `field-filled`), в разметке — как обычный класс;
  - встречается один раз → классы прямо в разметке.
- Выносить по повторению и смыслу, а не по числу классов: элемент на один раз с длинным списком классов остаётся на месте (длинный список — массивом по группам, `ui.md`). `@utility` заводи только для узнаваемой роли, не для каждых двух-трёх классов.

## Экран с прокруткой

Экран, где в шапке есть поле ввода (поиск) или список может быть длинным, — `<Screen fit>` и внутри него `ScrollArea`: прокручивается только `ScrollArea`, а `PageHeader` над ней стоит на месте. Всю страницу с прилипающей шапкой (`sticky`) не прокручивать: iOS рисует каретку поля в такой шапке мимо поля. `PageHeader` своего фона не имеет и не прилипает. Сообщения о состоянии внутри `ScrollArea` (`Message`: пусто, ничего не найдено, ошибка) — `class="flex-none"`, сразу под шапкой, а не по центру: клавиатура меняет высоту окна рывком, и сообщение по центру прыгало бы. Состояния списка — компонент `ListState`, экран задаёт только `empty` и `children`. Образец — `routes/notes/+page.svelte`. `overflow-hidden` на `Screen` не ставить: он делает `Screen` контейнером прокрутки. По горизонтали `Screen` уже обрезает содержимое (`overflow-x-clip`, контейнер прокрутки не создаёт): слишком широкий элемент не делает экран прокручиваемым вбок. Длинный текст от пользователя (названия) всё равно переносится сам — `wrap-break-word`, как заголовок `PageHeader`.

Кнопка сохранения формы (настройки счётчика) — последний элемент формы: `<ActionBar class="static">`, до неё долистывают. Прилипшая к низу окна, она лежит поверх полей. Образец — `CounterForm.svelte`.

## Доступность

У кнопки-иконки — `aria-label` (или prop `label`, как у `FloatingButton`), у поля — подпись (видимая или `sr-only`), у сообщений о состоянии — роль (`status` / `alert`, как у `Message`), заголовки — по уровням страницы.
