# e2e-тесты (Playwright)

Правила unit- и интеграционных тестов — в `tests.md`; здесь — только сценарии в Mini App через браузер. Покрыть модуль e2e-тестами по этим правилам — скилл `/cover-module <модуль>`. Playwright в проект ещё не подключён: правила готовы заранее, при подключении — `tests/playwright.config.ts` (см. «Конфиг»), тип `e2e` в `tests/run-tests.ts` (`bun run test:e2e [модуль]`), правило Biome `noFloatingPromises` (см. «Гонки»), `motion-reduce:` у анимированных компонентов (см. «Конфиг») и строка в README/CLAUDE.md.

## Когда и как запускаются

- Только вручную и перед деплоем; в CI (`.github/workflows/ci.yml`) e2e не входят — они долгие и чувствительны к окружению.
- Приложение запускается через `webServer` Playwright: `vite dev` с `DEV_TELEGRAM_ID` (вход без `initData`, см. CLAUDE.md) и тестовой БД (`postgres-test`, как у интеграционных тестов). Настоящий Telegram в тестах не используется. Рабочая БД и `.env` с секретами e2e не нужны.
- Проверяется несколько сквозных сценариев на модуль (создать → найти → изменить → удалить, ошибка сети, «Назад»), а не каждая кнопка. Логику и граничные случаи покрывают unit- и интеграционные тесты.
- Бэкенд настоящий (API SvelteKit и тестовая БД), записанных ответов API (моков) нет. Подмена сети — только для сценариев ошибки, через `page.route` до действия: `await page.route('**/api/notes', (route) => route.abort())` — нет связи, `route.fulfill({ status: 500 })` — сбой сервера. Проверяется то, что видит пользователь (сообщение об ошибке — `answerDialog`, см. «Диалоги»).
- Наборы — тегами Playwright: `test('…', { tag: '@smoke' }, …)`, запуск части — `bun run test:e2e --grep @smoke`. Теги: `@smoke` — основной путь каждого модуля (создать → открыть → удалить); остальное — без тега. Новый тег — сюда же, с назначением.
- Отчёт — Allure: репортер `allure-playwright` пишет результаты в `tests/allure-results/`, отчёт собирается и открывается командой `bun run test:e2e:report` (обе папки — в `.gitignore`). Шаги `step()` попадают в Allure как шаги с номерами; модуль теста — метка `feature` (ставится в фикстурах по папке модуля, вручную в тестах не пишется). Встроенный HTML-отчёт Playwright с трассировкой остаётся для отладки упавшего теста.

## Конфиг Playwright

- **Устройства — три проекта на WebKit** (движок Safari и WebView Telegram на iOS; пользователи — в основном на iPhone, см. `ui.md`): маленький — iPhone SE 2/3 (375 × 667), средний — iPhone 15/16 (393 × 852), большой — iPhone 15/16 Pro Max (430 × 932). Размеры — из описаний устройств Playwright (`devices[...]`), а где нужного нет — `viewport` и `isMobile`/`hasTouch` константами в конфиге. Шапку Telegram не моделируем: размер — экран устройства. Каждый сценарий проходит на всех трёх; Chromium — только для отладки (`--project`).
- **При падении** — скриншот и трассировка (`screenshot: 'only-on-failure'`, `trace: 'retain-on-failure'`): Allure прикладывает их к упавшему тесту, у прошедших ничего не хранится.
- **Без анимаций**: `reducedMotion: 'reduce'` в `use`. Анимированные компоненты Mini App (переходы `SwipeActions`, `transition-*`) уважают это через `motion-reduce:transition-none` — тесты не ждут конца перехода, а пользователи с настройкой «Уменьшить движение» его не видят.
- `workers: 1`, `fullyParallel: false` — см. «Гонки», п. 5.

## Экраны: BasePage и компоненты

- `BasePage` (абстрактный класс в `base.page.ts`) — только то, что есть у **каждого** экрана: `page`, адрес экрана (`path`), `open()`, `expectOpened()`, `goBack()`. Кнопка «Назад» Telegram нативная и живёт вне страницы — Playwright её не видит, поэтому `goBack()` идёт по истории браузера.
- Экран наследует `BasePage` и добавляет своё: `CounterPage.increment()` есть только у экрана счётчика.
- Элемент, который есть лишь на части экранов (поиск, строка со свайпом, пустое состояние списка), — объект компонента в `components/` (`<элемент>.component.ts`), экран подключает его полем (`readonly searchBar = new SearchBarComponent(this.page)`). В `BasePage` такие методы не добавляются: у экрана без поиска не должно быть `search()`.

## Класс экрана

Разделы — в этом порядке, отделены комментарием-заголовком:

1. **Элементы** — `readonly` поля (`titleInput`) или методы с параметром (`noteCard(title)`), описанные один раз через `getByTestId(TestId.…)` (см. «Элементы и `data-testid`»). Дальше методы и тесты обращаются к ним по имени (`this.titleInput`), `getBy…` вне раздела элементов не пишется.
2. **Действия** — то, что делает пользователь, названное по смыслу: `openNewNote()`, `fill(title, content)`, `search(query)`, `deleteNote(title)`. Не `clickButton()`, не `tap…()` (в Playwright `tap` работает только в режиме сенсорного экрана).
3. **Проверки** — методы `expect…` (см. ниже).
4. **Удобные методы** — цепочки действий *этого* экрана, которые повторяются в тестах (`fillAndWaitSaved(title, content)` — заполнить и дождаться автосохранения).

Адрес экрана — полем `path` класса, а не строкой в тестах.

## Элементы и `data-testid`

Аналог `accessibilityIdentifier` из iOS: атрибут `data-testid` не виден пользователю и экранному диктору, он нужен только тестам. Элементы ищутся по нему, а не по тексту и роли: тесты не ломаются при правке текстов и вёрстки.

- **Константы — один источник** для приложения и тестов: `apps/web/src/lib/constants/test-ids.ts`, объект `TestId` (`as const`), сгруппированный по экранам. Значение — `'<экран>.<элемент>'` в kebab-case: `TestId.NoteEditor.Title = 'note-editor.title'`. Элементы базовых компонентов `ui/`, которые есть на многих экранах (плавающая кнопка, поиск, пустое состояние списка, кнопка удаления в строке со свайпом), — группа `TestId.Common` (`'common.<элемент>'`): идентификатор ставит сам компонент, экраны его не дублируют. Когда файл разрастётся — папка `constants/test-ids/` с файлом на экран и `index.ts`, собирающим `TestId`. Строки-идентификаторы вручную нигде не пишутся — ни в компонентах, ни в тестах. Файл без зависимостей (не импортирует `$app/*`), поэтому его импортируют и компоненты (`#lib/constants/test-ids.ts`), и тесты (`#web/lib/constants/test-ids.ts` — алиас `#web/*` в `tests/tsconfig.json`).
- **Атрибут ставится только на элементы, с которыми работают тесты**: кнопки и поля, которые тест нажимает или заполняет, контейнеры, которые он проверяет (список, пустое состояние, сообщение об ошибке). Не на каждый `div`.
- **В компоненте**: `data-testid={TestId.NoteEditor.Title}`. Компоненты `ui/` передают атрибут дальше через `{...rest}` (как `Card`, `Button`); если компонент `rest` не принимает — добавить.
- **Повторяющиеся элементы** (карточки списка): один идентификатор на все, нужная выбирается по содержимому — `this.page.getByTestId(TestId.NotesList.Card).filter({ hasText: title })`; кнопка внутри карточки — от карточки (`this.noteCard(title).getByTestId(TestId.NoteCard.Delete)`). `nth()` — нет.
- **Идентификатор со значением** — когда текст не различает элементы (две записи с одинаковым названием) или тест знает id записи из фабрики: `testIdWithValue(TestId.CountersList.Row, counter.id)` → `'counters-list.row=<id>'` (функция — в том же `test-ids.ts`). Значение — id записи или вариант (`testIdWithValue(TestId.Counters.Tab, 'paused')`). И компонент, и тест строят его этой функцией — строка `=` вручную не пишется.
- **Состояние элемента** (выбрана вкладка, включён переключатель, раскрыт блок) — стандартными атрибутами доступности, а не классом или своим атрибутом: `aria-selected` у вкладок `SegmentedControl`, `role="switch"` + `aria-checked` у `Switch`, `aria-expanded`, `disabled`. Тест проверяет их встроенными проверками: `toBeChecked({ checked })`, `toHaveAttribute('aria-selected', 'true')`, `toBeDisabled()`; экранный диктор читает то же состояние.
- **Данные проверяются на элементе с идентификатором**: `await expect(this.noteCard(title)).toContainText(content)`. Текст в тесте — это проверяемые данные, а не способ найти элемент.
- Доступность от этого не отменяется: у кнопки-иконки обязателен `aria-label`, у поля — подпись (`ui.md`), просто тесты на них не опираются.
- CSS- и Tailwind-классы, структура DOM, `nth()` в локаторах — нет.

```ts
// apps/web/src/lib/constants/test-ids.ts
export const TestId = {
	NotesList: { Search: 'notes-list.search', Card: 'notes-list.card', Empty: 'notes-list.empty' },
	NoteCard: { Delete: 'note-card.delete' },
	NoteEditor: { Title: 'note-editor.title', Content: 'note-editor.content' },
	Common: { FloatingButton: 'common.floating-button', SwipeDelete: 'common.swipe-delete' },
} as const;

/** Идентификатор со значением: `counters-list.row=<id>`. */
export function testIdWithValue(id: string, value: string): string {
	return `${id}=${value}`;
}

// tests/e2e/notes/note-editor.page.ts — кнопки «Сохранить» нет: редактор сохраняет сам
export class NoteEditorPage extends BasePage {
	// --- Элементы ---
	readonly titleInput = this.page.getByTestId(TestId.NoteEditor.Title);
	readonly contentInput = this.page.getByTestId(TestId.NoteEditor.Content);

	// --- Действия ---
	async fill(title: string, content = ''): Promise<void> {
		await this.titleInput.fill(title);
		await this.contentInput.fill(content);
	}
}
```

## Проверки в классе экрана

Проверку можно и нужно выносить в метод экрана, если она повторяется или состоит из нескольких `expect` — тест тогда читается как сценарий.

- Метод называется `expect…` (`expectNoteVisible(title)`, `expectEmptyState()`, `expectErrorMessage(text)`) и содержит web-first `expect`.
- **Метод знает, *как* проверить, тест передаёт, *что* ожидается**: ожидаемые данные (название заметки, текст ошибки) — аргументами из теста. Внутри метода допустимы только неизменные состояния самого интерфейса (заглушка пустого списка, заголовок экрана).
- В методах проверки нет ветвлений (`if`) и «мягких» проверок, меняющих ход теста: метод либо проходит, либо падает.
- Два противоположных состояния одного элемента — один метод с флагом, если флаг уходит прямо в проверку Playwright: `expectSearchVisible(visible = true)` → `await expect(this.searchBar).toBeVisible({ visible })` (так же `toBeChecked({ checked })`, `toBeEnabled({ enabled })`). Разные пути внутри метода по флагу — нет: это уже два метода.

## Шаги: `step()`

- Тест делится на шаги обёрткой `step(title, body)` из `step.ts`, а не прямым `test.step`. Обёртка сама нумерует шаги верхнего уровня в пределах теста («1. Открытие списка», «2. Создание заметки») и задаёт `{ box: true }` — ошибка указывает на строку теста, а не на глубину класса. Номера вручную не пишутся: вставка шага в середину не требует перенумерации.
- Названия шагов — в том же именном стиле, что описания тестов (`tests.md`, «Оформление»): с заглавной буквы, с отглагольного существительного — «Открытие списка», «Удаление счётчика», а не «Открыть список». Описание шага внутри метода проверки — тоже существительным: `` `Проверка заметки «${title}» в списке` ``.
- Внутри шага — последовательные `await` вызовов экранов. Цепочки через точку (`counter.increment().reset()`) не используются: методы асинхронные, а самописная асинхронная цепочка плохо отлаживается.

```ts
// notes/crud.spec.ts
test('Нахождение созданной заметки поиском', async ({ notesList, noteEditor }) => {
	await step('Создание заметки', async () => {
		await notesList.open();
		await notesList.openNewNote();
		await noteEditor.fillAndWaitSaved('Покупки', 'молоко');
	});
	await step('Поиск заметки', async () => {
		await notesList.search('покуп');
		await notesList.expectNoteVisible('Покупки');
	});
});
```

## flows/: цепочки через несколько экранов

- Функция, которая проводит пользователя через **два и более экрана** (аналог `loginUser()`): `createNoteViaUi(notesList, noteEditor, title)`, `createCounterViaUi(countersList, counterForm, input)` (`counters/flows/create-counter.ts`: список → форма → экран счётчика), `openSection(mainMenu, 'Заметки')`. Ни одному экрану она не принадлежит, поэтому не метод класса.
- Лежит в `tests/e2e/<модуль>/flows/<цепочка>.ts`. Цепочка через несколько модулей — в модуле, которым сценарий заканчивается: переход из уведомления раздела «Напоминания» на экран счётчика — в `counters/flows/`, хотя начинается на экране `reminders`.
- Правило: если в рамках одного теста последовательность действий затрагивает два и более экрана — она оформляется flow, а не пишется в тесте вызовами разных экранов подряд. Действия и проверки в пределах одного экрана — вызовами этого экрана прямо в тесте. Проверки, которые и есть цель сценария, остаются в тесте (flow может завершаться проверкой, что переход удался).
- Если тесту нужны только исходные данные, а путь через интерфейс не важен, — фабрика из `tests/helpers/factories.ts` (быстрее и надёжнее), а не flow.

## Диалоги подтверждения и сообщения

Вне Telegram (а e2e идут в обычном браузере) `confirmDialog` и `alertDialog` (`lib/telegram.ts`) — это `window.confirm` и `window.alert`. Playwright по умолчанию сам закрывает такой диалог отменой: без обработчика «Удалить?» тихо отменяется, и тест падает дальше, на проверке, с непонятной причиной.

- Диалог ждётся подпиской **до** действия, которое его вызывает (правило 4 из «Гонок»), а его текст — проверяемые данные из теста. Один метод в `BasePage` — диалог может появиться на любом экране:

  ```ts
  // base.page.ts — action вызывает диалог; true — согласиться, false — отказаться
  protected async answerDialog(action: () => Promise<void>, message: string, accept = true) {
  	const dialog = this.page.waitForEvent('dialog');
  	const done = action(); // click не завершится, пока диалог открыт
  	const shown = await dialog;
  	expect(shown.message()).toContain(message);
  	await (accept ? shown.accept() : shown.dismiss());
  	await done;
  }

  // counter.page.ts
  async remove(title: string): Promise<void> {
  	await this.answerDialog(() => this.deleteButton.click(), `счётчик «${title}»`);
  }
  ```

- `page.on('dialog', …)` на весь тест — нет: такой обработчик молча примет и неожиданный диалог (например, сообщение об ошибке), и тест пройдёт там, где должен упасть.
- Ошибка действия в Mini App — тоже диалог (`alertDialog`): сценарий «ошибка сети» проверяет его текст тем же методом с `accept` (у `alert` одна кнопка).

## Удаление свайпом

Строки списков (`SwipeActions`) открывают кнопку «Удалить» свайпом влево; жест сделан на pointer-событиях и принимает мышь, поэтому в e2e это движение мыши, а не `tap` (сенсорный режим не нужен).

- Свайп — метод компонента строки `SwipeRowComponent.swipeOpen()` (`components/swipe-row.component.ts`): `page.mouse.down()` на строке, `mouse.move()` влево больше чем на половину ширины действий **с промежуточными шагами** (`{ steps: 10 }` — иначе приходит одно событие `pointermove`, и жест не распознаётся), `mouse.up()`. Координаты — от `boundingBox()` строки, а не числами.
- Удаление в экране списка — `swipeToDelete(title)`: свайп строки → кнопка удаления строки (`TestId`) → `answerDialog` с подтверждением. Проверка — что строки больше нет (`expect(row).toHaveCount(0)`), а не что свайп «сработал».
- Удаление с экрана элемента (кнопка «Удалить» в редакторе или на экране счётчика) — отдельный сценарий: это другой путь в коде.

## Гонки: стандарт написания

Последовательные `await` гонок между шагами не создают: следующая строка выполняется после завершения предыдущей. Гонка возникает между тестом и приложением (запрос, перерисовка) и между параллельными тестами. Правила, обязательные для каждого e2e-теста:

1. **Каждое действие и каждая проверка — с `await`.** Забытый `await` отправляет действие в фон, и тест идёт дальше — самая частая настоящая гонка. Ловит правило Biome `noFloatingPromises` (включить вместе с Playwright).
2. **Только web-first проверки.** `await expect(locator).toHaveText('…')` повторяет проверку, пока условие не выполнится. Прочитать значение и сравнить (`const text = await locator.textContent(); expect(text).toBe('…')`) — нет: это снимок в один момент, без ожидания.
3. **Никаких пауз.** `page.waitForTimeout`, `sleep`, `setTimeout` — нет. Ждём состояние (`expect(locator)…`), событие или ответ — не время.
4. **Событие, которое вызывает само действие, ждём с подпиской *до* действия**, иначе ответ может прийти раньше подписки:

   ```ts
   const saved = page.waitForResponse('**/api/notes');
   await noteEditor.fill('Покупки'); // автосохранение отправит POST
   await saved;
   ```

5. **Один процесс на тестовую БД.** Тесты разных файлов по умолчанию идут параллельно; с общей БД `testDatabase.reset()` одного теста сотрёт данные другого. В `playwright.config.ts` — `workers: 1` (и `fullyParallel: false`). Отдельная БД на процесс — только если понадобится скорость.
6. **Тест не зависит от других тестов и порядка запуска**: готовит свои данные сам, перед тестом БД очищается (`testDatabase.reset()`).
7. **Действия не ждут вручную готовности элемента.** Перед `click`/`fill` локатор сам ждёт, что элемент появился, видим, не двигается и доступен; лишние `waitFor()` перед действием не пишутся. `locator.waitFor()` — только когда нужно дождаться элемента без действия и без проверки.

## Данные

- Данные, которые не проверяются в этом сценарии, создаются фабриками из `tests/helpers/factories.ts` (`createTestNote`, `createTestCounter`, `createTestNotification`); через интерфейс — только то, что проверяет сценарий. Новый модуль добавляет свою фабрику вместе с тестами.
- Воркер в e2e не запускается: то, что создаёт он (уведомления об окончании цикла — `CounterNotification`), создаёт фабрика `createTestNotification` (она завершает цикл тем же `processDue`, что и воркер). Окончание цикла на экране счётчика воркера не ждёт — Mini App сам вызывает `finish`. Сервис не даст создать цикл, который уже кончился, поэтому такой счётчик готовится фабрикой с коротким таймером и прямым сдвигом его `startAt`/`targetAt` в прошлое (правка записи — только для состояния, которого сервисы не создают, `tests.md`).
- Время в браузере (обратный отсчёт, «осталось 5 минут») — через `page.clock` Playwright (установить до `open()`), а не ожиданием: сервер при этом живёт по настоящему времени, поэтому то, что решает сервер (окончание цикла), готовится данными, а не часами браузера.
- Описания `test` — по-русски в именном стиле, как в остальных тестах (`tests.md`, «Оформление»): «Удаление заметки свайпом из списка»; `test.describe` — название экрана или сценария.
